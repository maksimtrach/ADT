# Codex Task: Audit Data Transformation Prototype

Создаем новый независимый проект **Audit Data Transformer («Конструктор расшифровок»)**.

Рабочая директория:
`/media/maksim/Data/Projects/AudDataTrans/`

Референсный проект (EMP):
`/media/maksim/Data/Projects/emp-reference/`

## 0. Основные инструкции

1. Новый проект разрабатывается исключительно в рабочей директории Audit Data Transformer.
2. Проект Engagement Management Platform (EMP) используется только как источник информации.
3. Не изменяй, не удаляй и не перемещай файлы EMP.
4. Не запускай миграции, команды установки зависимостей или другие операции, изменяющие EMP.
5. Не копируй из EMP секреты, `.env`, ключи, учетные данные, базы данных и клиентские файлы.
6. Изучи frontend EMP, чтобы воспроизвести его дизайн-систему:
   - цветовую палитру;
   - типографику;
   - компоненты;
   - расположение элементов;
   - формы;
   - таблицы;
   - состояния загрузки и ошибок.
7. По возможности переиспользуй подходы и компоненты интерфейса, но не создавай runtime-зависимость от EMP.
8. Не переноси сложную backend-архитектуру EMP, если она не требуется для прототипа.

## 1. Контекст проекта

Необходимо разработать демонстрационный прототип модуля **«Конструктор расшифровок» (Audit Data Transformer)**.

Прототип предназначен для демонстрации возможностей интеллектуальной обработки нестандартных бухгалтерских выгрузок и преобразования их в стандартизированные плоские таблицы.

Разработка выполняется с использованием существующего проекта **Engagement Management Platform (EMP)** в качестве источника визуального стиля, компонентов интерфейса и архитектурных решений.

**Важно:** сначала изучи существующий репозиторий EMP. Не начинай реализацию до анализа структуры проекта, дизайн-системы и доступных компонентов.

Цель — получить минимальный, но функциональный прототип, который можно продемонстрировать руководителю автоматизации.

## 2. Основные ограничения

- Только две пользовательские страницы: Login и Data Transformation.
- Не создавать полноценную систему управления проектами.
- Не реализовывать сложную ролевую модель.
- Не разрабатывать интеграцию с другими модулями EMP.
- Не изменять существующую функциональность EMP без необходимости.
- Не создавать микросервисную архитектуру.
- Не реализовывать сложный визуальный редактор правил парсинга.
- Не создавать искусственные демонстрационные результаты, выдаваемые за настоящую обработку файлов.
- Не реализовывать поддержку PDF и OCR.
- Не усложнять прототип функциональностью, которая не требуется для демонстрации.

Прототип должен быть простым, визуально качественным и действительно выполнять преобразование файлов.

## 6. Страница 2 — Обработка файлов

Это основная страница приложения.

Предлагаемая структура:

### Header

- Название «Конструктор расшифровок».
- Имя текущего пользователя.
- Кнопка выхода.

### Блок A. Загрузка файла

Реализуй карточку «Новое преобразование».

Элементы:

**Загрузка файла**
- Drag & Drop.
- Кнопка выбора файла.
- Поддержка XLSX.
- Отображение названия и размера файла.
- Проверка расширения и размера.

**Тип исходных данных**

Выпадающий список:
- Оборотно-сальдовая ведомость (ОСВ).
- Журнал проводок.

**Целевой формат**

Выпадающий список доступных шаблонов плоской таблицы.

Для ОСВ:
- Счет.
- Субсчет.
- Наименование счета.
- Сальдо на начало Дт.
- Сальдо на начало Кт.
- Оборот Дт.
- Оборот Кт.
- Сальдо на конец Дт.
- Сальдо на конец Кт.

Для журнала проводок:
- Дата.
- Номер документа.
- Счет Дт.
- Счет Кт.
- Аналитика Дт.
- Аналитика Кт.
- Сумма.
- Содержание операции.

Предусмотри отображение описания выбранного шаблона.

Если отдельные поля отсутствуют в исходном файле, система должна показывать их как отсутствующие, а не выдумывать значения.

**Кнопка**

«Преобразовать файл».

Кнопка доступна после выбора файла, типа данных и целевого шаблона.

### Блок B. Статус обработки

После запуска отображай реальные этапы обработки:

1. Анализ структуры файла.
2. Определение колонок и группировок.
3. Формирование правил преобразования.
4. Преобразование данных.
5. Контроль результата.
6. Формирование выходного файла.

Отображай текущий этап и итоговый статус.

Не имитируй прогресс обработки таймерами.

### Блок C. Результат преобразования

После завершения обработки отображай:

- Название исходного файла.
- Тип данных.
- Количество обработанных записей.
- Количество необработанных строк.
- Контрольные суммы, если их удалось определить.
- Выявленные ошибки или предупреждения.
- Предпросмотр первых 50–100 записей результирующей таблицы.

Добавь кнопки:
- «Скачать Excel».
- «Обработать повторно».

Если результат не прошел проверки, покажи соответствующее предупреждение.

Не отображай статус «Проверено», если контрольные процедуры не были выполнены или выявлены существенные расхождения.

### Блок D. Замечания к результату

Добавь текстовое поле:

«Что необходимо исправить в результате?»

Пример замечания:

«Контрагенты после строки 150 относятся к счету 62.02, а не 62.01».

Кнопка «Исправить и обработать повторно».

Backend должен принимать замечание, передавать его в модуль анализа, формировать обновленную спецификацию и повторно выполнять преобразование.

Если LLM недоступна, функция должна корректно сообщать об этом, а не имитировать исправление.

### Блок E. История преобразований

В нижней части страницы размести таблицу:

- Дата и время.
- Исходный файл.
- Тип данных.
- Целевой формат.
- Количество записей.
- Статус.
- Действия.

Действия:
- Открыть результат.
- Скачать Excel.
- Повторить преобразование.

История должна сохраняться на backend и оставаться доступной после обновления страницы.

Для прототипа достаточно локального хранилища метаданных, например SQLite, если это не противоречит существующей архитектуре.

## 7. Backend обработки файлов

Реализуй минимальный, но расширяемый pipeline.

### 7.1. File Profiler

Считывает исходный XLSX и определяет:

- Листы.
- Используемые диапазоны.
- Заголовки.
- Объединенные ячейки.
- Формулы.
- Числовые колонки.
- Повторяющиеся шаблоны строк.
- Возможные группировки и итоги.

Не ограничивай исследование первыми строками файла.

### 7.2. LLM Planner

Получает структурное представление файла и целевой формат.

Возвращает формальную JSON-спецификацию преобразования.

Спецификация должна содержать:
- Область исходных данных.
- Правила распознавания строк.
- Правила определения колонок.
- Правила наследования аналитических признаков.
- Правила исключения итоговых строк.
- Сопоставление исходных полей с целевыми.
- Описание контрольных соотношений.

Валидируй спецификацию через Pydantic.

Не разрешай LLM генерировать и выполнять произвольный Python-код.

### 7.3. Parsing Engine

Детерминированно выполняет спецификацию.

Минимально необходимые операции:
- Выбор диапазона.
- Определение типа строки.
- Извлечение значений.
- Наследование значения группировки.
- Исключение итогов.
- Нормализация чисел и дат.
- Сопоставление колонок с целевым форматом.

Сохраняй ссылки на исходные строки и ячейки.

### 7.4. Validation Engine

Реализуй базовые проверки:
- Учет обработанных и необработанных строк.
- Проверка преобразования числовых значений.
- Проверка контрольных итогов, если они доступны и надежно определены.
- Выявление отсутствующих обязательных полей.
- Выявление неоднозначных результатов.

Используй LLM для дополнительной диагностики структуры, но не вместо программных проверок.

### 7.5. Повторная обработка

При замечании пользователя:
1. Найди исходный файл и использованную спецификацию.
2. Передай замечание и релевантные исходные данные в LLM Planner.
3. Получи измененную спецификацию.
4. Проверь допустимость изменений.
5. Выполни повторное преобразование.
6. Повтори контроль.
7. Сохрани новую версию результата.

Сохраняй предыдущую версию, чтобы можно было сравнить результаты.

Ограничь количество автоматических попыток исправления.

## 8. API

Предусмотри минимальный REST API:

- POST /auth/login
- POST /transformations
- GET /transformations
- GET /transformations/{id}
- GET /transformations/{id}/preview
- GET /transformations/{id}/download
- POST /transformations/{id}/retry

API должен выполнять серверную проверку авторизации.

Не используй публичные ссылки на скачивание файлов. Скачивание должно проходить через авторизованный backend.

## 9. Безопасность

Прототип будет работать с потенциально конфиденциальными бухгалтерскими данными.

Поэтому:
- Не отправляй файлы во внешние LLM без явно настроенного и разрешенного провайдера.
- По умолчанию внешние LLM-вызовы должны быть отключены.
- Не записывай содержимое бухгалтерских файлов в обычные application logs.
- Проверяй размер и формат файлов.
- Защити приложение от path traversal.
- Не исполняй Excel-макросы.
- Не выполняй код, полученный от LLM.
- Ограничь доступ к файлам авторизованными пользователями.
- Храни секреты в переменных окружения.

Не используй реальную клиентскую информацию в тестовых данных.

## 10. Демонстрационные файлы

Подготовь синтетические тестовые XLSX-файлы:

1. Простая ОСВ.
2. ОСВ с многоуровневыми группировками.
3. ОСВ с объединенными ячейками и промежуточными итогами.
4. Журнал проводок с нестандартными заголовками.

Для каждого файла подготовь ожидаемый результат в формате плоской таблицы.

Эти файлы должны использоваться для автоматических тестов.

Прототип должен действительно обрабатывать файлы, а не возвращать заранее подготовленные результаты по имени файла.

## 11. Критерии готовности

Прототип считается готовым, если:

1. Пользователь может авторизоваться.
2. Пользователь может загрузить XLSX.
3. Пользователь может выбрать тип данных и целевой формат.
4. Система выполняет реальное преобразование файла.
5. Результат отображается в виде плоской таблицы.
6. Пользователь видит результаты контрольных процедур.
7. Результат можно скачать в XLSX.
8. История преобразований сохраняется.
9. Пользователь может отправить замечание и повторить обработку при доступной LLM.
10. Интерфейс соответствует стилю EMP.

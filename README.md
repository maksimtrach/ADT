# Audit Data Transformer — Конструктор расшифровок

Локальный прототип преобразования нестандартных бухгалтерских XLSX-выгрузок в стандартизированные плоские таблицы. Интерфейс следует дизайн-системе EMP, но проект не имеет runtime-зависимости от EMP.

## Возможности

- безопасный вход по email/паролю и серверные сессии в `HttpOnly` cookie;
- роли `USER` и `ADMIN`;
- загрузка и реальная обработка XLSX;
- ОСВ и журнал проводок;
- полный profiler книги, детерминированный parser и контроль результата;
- многострочные шапки и динамические уровни аналитики из одной иерархической колонки;
- LLM Planner с именованными профилями Ollama и OpenAI-compatible, выбором активной модели и fallback;
- повторная обработка по замечанию с сохранением предыдущей версии;
- просмотр первых 100 строк исходного XLSX перед запуском обработки и первых 100 строк результата; защищённое скачивание XLSX;
- отдельная история преобразований;
- техническое мемо каждого нового запуска: исходные строки, правила, LLM-запрос и ответ, проверки и экспорт;
- административный журнал действий;
- отдельная переносимая память подходов общей ОСВ: черновики, подтверждение, версии, частные и общие подходы, импорт/экспорт;
- четыре синтетических XLSX-набора с ожидаемыми результатами.

## Требования

- Node.js 22+ и npm 10+;
- Python 3.12+;
- хотя бы один доступный LLM-профиль из `config/llm.toml` (LLM необязательна для первичной детерминированной обработки).

## Предпросмотр исходного файла

После выбора XLSX файл передаётся на сервер один раз: блок загрузки показывает первые 100 физических строк активного листа в прокручиваемом окне высотой около 12 строк. Для нескольких листов доступен выбор листа предпросмотра; он не меняет правила определения листа при преобразовании. Пустые строки и номера строк сохраняются. Используются сохранённые значения формул, вычисление формул не выполняется. Предпросмотр ограничен первыми 120 колонками с явной отметкой об усечении. Кнопка «Преобразовать» использует уже загруженный файл. Неиспользованные временные файлы недоступны после 24 часов и удаляются при следующей загрузке.

## Профили документов и переносимая память

Первый выпуск вводит реестр пяти семейств документов. Общая ОСВ и журнал проводок
используют существующие обработчики и прежние значения API `TRIAL_BALANCE` / `JOURNAL`.
ОСВ по отдельному счёту, баланс и отчёт о прибылях и убытках зарегистрированы как
запланированные профили и пока недоступны для выбора. Реестр доступен по
`GET /api/transformations/document-profiles`. Существующие спецификации читаются как
версия 1; новые сохраняют `schema_version` явно. Миграция старой истории не нужна.

Настройки в `.env`:

```env
DOCUMENT_MEMORY_PATH=./document-memory
DOCUMENT_MEMORY_ENABLED=true
```

После изменения настроек перезапустите backend. Память хранится отдельно от основной
SQLite в `document-memory/library.json`. Файл содержит версию формата, карточки,
локальные права доступа, счётчики применений и до 5000 последних диагностических
случаев. Изменения защищены межпроцессной блокировкой и записываются атомарно;
повреждённое хранилище не перезаписывается. Папка исключена из Git. Отключение
`DOCUMENT_MEMORY_ENABLED` выключает автоматическое применение и накопление, но
сохраняет доступ к просмотру, ручному сохранению и переносу.

### Использование

1. После исправления сложной общей ОСВ, успешного резервного распознавания либо
   выявления нетривиального детерминированного дерева счетов автоматически сохраняется
   частный черновик подхода, если его структура поддерживается.
   Другой успешный результат можно сохранить кнопкой **Сохранить подход в память**:
   исходный файл повторно проверяется. Неудачные и неподдерживаемые случаи видны отдельно.
2. Откройте **Память обработки**, раскройте шапку и сопоставление колонок и проверьте
   назначение показателей. Совпадение арифметики не доказывает правильность их смысла.
   Подтвердите подход. Владелец управляет своими частными подходами, администратор
   дополнительно может публиковать общие. Общий подход доступен другим пользователям
   только после подтверждения; менять его может только администратор.
3. На новом файле при отсутствии уверенного решения правил проверяются доступные
   подтверждённые карточки. Для версии 1 требуется точное совпадение нормализованной
   шапки и физических колонок; строки шапки и название листа могут изменяться.
   Проверяются шапки глубиной до 5 строк в первых 100 строках, до 120 колонок.
4. Границы данных и итоговая строка определяются заново. Используются существующие
   проверки по всему файлу: счета, покрытие строк, значения формул, денежные показатели,
   построчный баланс и доступные итоги. Непройденная проверка отклоняет подход.
   Противоречащие карточки и несколько подходящих листов не выбираются произвольно.
   Явные комментарии пользователя обходят память. Уверенная обычная обработка
   дополнительных обращений к памяти не делает.
5. Если память не дала решения, остаётся текущий путь через LLM и уточнение пользователя.
   Недоступность памяти не блокирует преобразование. В техническом мемо отражаются
   поиск, проверки, отказ или применение с идентификатором и версией карточки.

Карточки не содержат исполняемого кода, абсолютных путей, денежных значений и
точечных подстановок. Хранятся нормализованная шапка, сопоставление полей, режим
строк и краткие сведения о проверке. Текст шапки может содержать названия организаций:
перед публикацией или передачей пакета его нужно просмотреть. Это не автоматическая
анонимизация произвольного содержимого Excel.

### Перенос и версии

Нажмите **Экспортировать память**, перенесите `document-memory.json` и импортируйте
его на другой установке. Экспорт включает видимые карточки и версии, но не включает
учётные записи, привязки к обработкам, исходные файлы и комментарии. При импорте
владельцем становится импортирующий пользователь; новые карточки всегда частные
черновики. Это позволяет переносить знания в установку с пустой основной БД и
другой моделью. Простая резервная копия всей папки сохраняет локальные идентификаторы
владельцев, поэтому для новой БД используйте именно экспорт/импорт.

Одинаковые версии с одинаковым содержимым пропускаются. Конфликт идентификатора,
владельца или содержимого отменяет весь импорт. Чужое семейство нельзя дополнить
новой версией. Новое сопоставление для той же шапки сохраняется отдельной версией;
старое содержимое не меняется. Среди доступных пользователю версий одного семейства
применяется только последняя, и только если она подтверждена. Черновик новой версии
приостанавливает применение старой доступной версии до проверки. Лимиты: 500 версий
карточек, пакет до 20 МБ. Поисковый индекс и отдельный векторный сервер не требуются.

### Границы первого выпуска

Повторное применение памяти поддерживает плоскую общую ОСВ и дерево счетов.
Многоуровневая аналитика, наследование полей и пользовательские подстановки пока
не превращаются в переиспользуемые карточки. Сложные случаи таких файлов отмечаются
как неподдерживаемые памятью; существующая обработка остаётся доступной.
Сохранённый подход является шаблоном конкретной шапки, а не универсальным правилом
для произвольной перестановки столбцов. Нечёткий поиск, примеры памяти в LLM,
управляемое дополнительное исследование файла, фоновое обобщение, несколько областей
документов и новые обработчики — следующие этапы. Новая память не пополняется
массовым импортом прежних преобразований.

API памяти: `GET /api/document-memory`, `GET /cases`, `GET /export`,
`POST /import` (multipart `file`), `POST /{card_id}/status` и
`POST /from-transformation/{transformation_id}` относительно `/api/document-memory`.
Подтверждения, ручные сохранения и переносы отражаются в административном журнале.

## Настройка LLM

Подключения описаны в `config/llm.toml`. По умолчанию выбран удалённый OpenAI-compatible профиль `remote_qwen35`, а локальная Ollama используется как резервный:

```toml
active_profile = "remote_qwen35"
fallback_profiles = ["local_ollama"]

[profiles.remote_qwen35]
enabled = true
protocol = "openai"
base_url = "http://192.168.1.65:1234/v1"
model = "qwen/qwen3.5-9b"
timeout_seconds = 180
connect_timeout_seconds = 5
thinking = false

[profiles.remote_qwen35.generation]
temperature = 0
max_tokens = 1800
```

`timeout_seconds` ограничивает полное ожидание генерации, а `connect_timeout_seconds` — только установление соединения; короткий connect timeout быстро переключает недоступный удалённый профиль на резервный.

Доступны протоколы `ollama` (`/api/chat`) и `openai` (`/v1/chat/completions`). Активный профиль можно сменить в TOML или без изменения файла:

```env
LLM_PROFILE=local_ollama
```

Для сервера с авторизацией в профиле указывается только имя переменной:

```toml
api_key_env = "REMOTE_LLM_API_KEY"
```

Сам токен задаётся в `.env` или окружении процесса. Он не попадает в конфигурационный файл и техническое мемо. Изменения применяются после перезапуска backend.

Если `config/llm.toml` отсутствует, сохраняется обратная совместимость со старыми переменными `LLM_PROVIDER`, `OLLAMA_URL`, `OLLAMA_MODEL` и `LLM_TIMEOUT_SECONDS`.

## Как работает LLM

Первичная обработка идёт по цепочке: анализ структуры → несколько спецификаций-кандидатов → пробный разбор → проверки → выбор. `RulePlanner` ищет многострочную шапку в первых 100 строках (до 5 уровней), учитывает объединённые ячейки и формирует до 12 вариантов, включая альтернативные колонки с похожими заголовками. `hypothesis_planner.py` проверяет фактические значения, покрытие строк и полей, сохранённые результаты формул, коды счетов, построчное равенство остатков и оборотов, а также независимые итоги, если они есть.

Групповые заголовки денежных периодов распознаются и без объединения ячеек: название над первой колонкой распространяется на соседнюю только при явной паре «Дебет/Кредит» или «Дт/Кт» ниже. Пустые разделительные столбцы и другие заголовки не пересекаются; исходные ячейки не изменяются. В схеме ответа резервной LLM номер колонки — строго целое число от 1 (`A=1`, `B=2`); отсутствие сопоставления обозначается `null`. Выход за границы конкретного листа и повторное использование колонок дополнительно проверяются в коде.

Однозначный проверенный вариант выполняется без LLM. Если осталось несколько правдоподобных вариантов, модель получает их заголовки, примеры значений и результаты проверок и возвращает только идентификатор выбранного варианта либо отказ от выбора.

Для общей ОСВ без подписей Дт/Кт добавляется стандартная гипотеза: первая денежная пара — Дт/Кт начала, вторая — Дт/Кт оборотов, третья — Дт/Кт конца. Она применяется только при трёх распознанных периодах, занимающих шесть последовательных колонок, и отсутствии явных подписей сторон. Предположение записывается в мемо, результат остаётся с предупреждением: арифметическое равенство само по себе не доказывает порядок сторон.

Исходные строки для LLM ограничиваются окном: вся найденная шапка, 3 строки перед ней и 5 после, включая пустые строки и с сохранением абсолютных координат. Это правило применяется к выбору кандидата, уточнению по комментарию и резервному распознаванию. При выборе нескольких кандидатов передаются окна их шапок без повторения строк. Если шапка не найдена, резервный контекст — первые 20 строк с явной отметкой. Случайные примеры из середины и конца книги больше не добавляются. Полные границы листа и статистика проверок сохраняются; Python продолжает проверять все данные.

Если подходящих вариантов нет или шапка не распознана, включается резервный `structure_recovery.py`. Модель получает описанное окно с координатами и объединениями, а также причины отклонения кандидатов. Ответ ограничен схемой `StructureAnswer`: лист, шапка, диапазон, сопоставление колонок и режим плоской таблицы либо дерева счетов. Вычисляемые поля, код, изменение значений и произвольное удаление строк запрещены. Границы, уникальность колонок, обязательные поля, покрытие исходных строк и контрольные соотношения проверяются повторно. При неудаче требуется конкретное уточнение; технические ошибки чтения или приложения не запускают этот режим. Текущий резервный режим не генерирует произвольные многоуровневые аналитические иерархии.

Для ОСВ с отдельными колонками счёта и наименования сохраняются названия, родительские счета, уровни и типы строк. Ведущие нули сохраняются по формату ячейки либо восстанавливаются по однозначному префиксу дочерних счетов. Все строки счетов остаются в результате; контрольные суммы рассчитываются только по верхнему уровню. Повторяющиеся счета не удаляются и отмечаются предупреждением. Итог без подписи в последней строке распознаётся по структуре и сверяется с этими суммами. Если независимых итогов нет, успешные построчные проверки позволяют обработку, но статус остаётся `WARNINGS`: арифметическая согласованность не равна независимому подтверждению сумм.

Валютные расшифровки и неподписанные строки сохраняются с привязкой к предыдущему счёту и исходной строке, исходным кодом/наименованием, валютой аналитики и отметкой о неподтверждённом типе суммы. Они исключены из общей агрегации; рублёвый эквивалент и валютная сумма не назначаются по догадке. Буквенные коды счетов (например, `ЗАБ`, `КВ`) поддерживаются. Если одинаковые корневые коды имеют разные наименования, ведущие нули не восстанавливаются автоматически, а общие суммы не рассчитываются до уточнения идентичности счетов. Все эти ограничения видны в мемо и на листе Excel «Контроль».

Повторный запуск без замечания заново строит правила. Однозначное указание вроде «Загрузи номера счетов из колонки C» применяется ко всему столбцу без LLM, удаляя прежние точечные подстановки этого поля. Поддерживается и полное сопоставление, например: «Бери номер счета из колонки A, наименование счета из колонки B, остатки по Дт/Кт колонки C и D, обороты Дт/Кт колонки E и F, остатки на конец по Дт/Кт колонки G и H». При полном сопоставлении ОСВ строится и проверяется без LLM даже при отсутствующей шапке и после ошибки предыдущего запуска. Кириллические буквы, похожие на латинские обозначения колонок, нормализуются; конфликтующие указания отклоняются. Частично распознанный комментарий не применяется молча. Свободный текст замечания обрабатывается моделью как ограниченная поправка к последней спецификации с последующей проверкой результата.

Пробелы в числовых ячейках считаются отсутствующим значением, а не ошибкой или подставленным нулём. Коды вроде `002`, `010`, `Н01` сохраняются. Распознанные строки контрагентов и валютные расшифровки сохраняются вместе с исходными значениями и ссылками на родительский счёт/аналитическую строку. Название «евро» распознаётся как EUR; отметка «в валюте» используется только при явном наличии в исходной строке. Служебная строка с подписью, но без сумм также остаётся в результате.

Последняя строка без счёта и наименования, содержащая все шесть числовых итогов после строки счёта, выделяется в `control_rows` отдельно от диапазона данных. Если сумма всех корневых счетов не совпадает с итогом, проверяется один фиксированный альтернативный состав: двухзначные корневые счета. Он принимается только при совпадении всех шести независимых итогов, без подбора произвольного набора строк. Остальные счета не удаляются из результата; их исключение из общей суммы явно отражается в предупреждении и на листе «Контроль». Несовпадение итогов остаётся ошибкой.

При выборе кандидата и резервном распознавании `fallback_profiles` используются только при транспортной ошибке модели. Отказ от выбора, недопустимый ответ или провал проверок не запускает перебор моделей. Для свободного текста замечания сохраняется режим уточнения спецификации с резервными профилями; такая обработка требует доступной LLM. Явное указание колонки и уверенная первичная обработка работают без модели.

Техническое мемо сохраняет кандидатов и доказательства выбора, применённые правила, а при обращении к LLM — профиль, протокол, адрес, модель, точный запрос и ответ, время выполнения и факт перехода на резервный профиль. В примерах исходных строк используются сохранённые значения формул с отдельной отметкой формульных колонок. Заголовок авторизации туда не записывается.

## Ограничения прототипа

- поддерживается только `.xlsx`, без PDF, OCR и макросов;
- формулы не вычисляются на backend — используются сохранённые Excel-значения;
- очередь задач выполняется внутри одного процесса FastAPI;
- файлы и SQLite хранятся локально в ignored-каталоге `data/`;
- сложные неоднозначные структуры могут потребовать пользовательского замечания;
- LLM-анализ большой книги может занимать заметное время, при этом UI показывает реальный этап обработки.
